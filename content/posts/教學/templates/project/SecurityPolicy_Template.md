# 安全政策範本（SECURITY.md）

> **參照標準**：GitHub Security Policy / ISO/IEC 29147:2018（弱點揭露）/ ISO/IEC 30111:2019（弱點處理流程）/ RFC 9116（security.txt）

> **文件用途**：告訴使用者與研究人員如何安全地通報弱點、會得到什麼回應、哪些版本仍受支援
>
> **適用階段**：專案建立時放入 Repository 根目錄或 `.github/`

## 1. 支援版本

### 📝 範本

```markdown
## 支援版本

| 版本 | 是否提供安全更新 |
|------|----------------|
| {x.y.z} | ✅ |
| < {x.0} | ❌ |
```

### 📖 使用說明

- 與 CHANGELOG、Release Note 的支援政策一致
- 不再支援的版本要明確寫出，避免使用者以為仍會修補

### 💡 範例

```markdown
## 支援版本

| 版本 | 是否提供安全更新 |
|------|----------------|
| 2.4.x | ✅ |
| 2.3.x | ✅（至 2027-03-31） |
| < 2.3 | ❌ |
```

## 2. 通報方式

### 📝 範本

```markdown
## 通報弱點

**請不要在公開 Issue 中回報安全問題。**

- 通報管道：{GitHub Private Vulnerability Reporting／security@{domain}}
- 加密：{PGP 公鑰連結（如有）}
- 請提供：受影響版本、重現步驟、影響說明、可行的修補建議（如有）
```

### 📖 使用說明

- 公開 Repository 建議啟用 GitHub 的 *Private vulnerability reporting*
- 內部系統可改為公司資安信箱，並在網站加上 `/.well-known/security.txt`（RFC 9116）

### 💡 範例

```markdown
## 通報弱點

**請不要在公開 Issue 中回報安全問題。**

- 通報管道：本 Repository 的「Security → Report a vulnerability」，或 security@company.com
- 請提供：受影響版本、重現步驟、影響說明
```

## 3. 處理流程與時限

### 📝 範本

```markdown
## 處理流程

| 階段 | 時限 |
|------|------|
| 確認收到 | {N} 個工作日內 |
| 初步評估（嚴重度） | {N} 個工作日內 |
| 修補 | 依嚴重度：Critical {N} 天、High {N} 天… |
| 公開揭露 | 修補發布後，與通報者協調 |
```

### 📖 使用說明

- 修補時限與公司弱點管理 SLA 一致（手冊 9.2）
- 嚴重度以 CVSS v4.0 評分，並參考 EPSS 與 CISA KEV

### 💡 範例

```markdown
## 處理流程

| 階段 | 時限 |
|------|------|
| 確認收到 | 2 個工作日內 |
| 初步評估（CVSS v4.0） | 5 個工作日內 |
| 修補 | Critical：24 小時內緩解、7 天內修復；High：7 天；Medium：30 天 |
| 公開揭露 | 修補發布後 30 天內，與通報者協調時間 |
```

## 4. 審查與驗證

> 本節供審查者使用，也用來檢查 AI 依本範本產出的 SECURITY.md 是否正確。

### 自動檢查

| 檢查項目 | 方法 |
|---------|------|
| 檔案存在 | CI 檢查 `SECURITY.md` 或 `.github/SECURITY.md` 存在 |
| 通報管道可用 | 每季寄送測試信或建立測試通報，確認有人回應 |
| 文件格式 | `npx markdownlint-cli2 SECURITY.md` |

### 人工審查問題

1. 支援版本表是否與實際維護狀況一致？
2. 通報信箱是否有人值守？
3. 處理時限是否與弱點管理 SLA 一致？

### AI 常見錯誤

- 承諾公司做不到的回應時限。
- 列出不存在或無人值守的通報信箱。
- 支援版本表與 CHANGELOG 不一致。
