# 需求追溯矩陣範本（Requirements Traceability Matrix, RTM）

> **參照標準**：ISO/IEC/IEEE 29148:2018（需求追溯）/ ISO/IEC/IEEE 29119-3:2021
>
> **文件用途**：串起「需求 → 設計 → 實作 → 測試」，確認每條需求都被實作與驗證，且每段程式都有需求依據
>
> **適用階段**：需求核准（G1）起持續維護，於設計核准（G2）與上線核准（G3）時檢查
>
> **範本版本**：v2.0（2026-10-06）｜對應《軟體開發標準程序教學手冊》v2.0 第 3.7、2.4 節

### 📖 使用說明

- 前向追溯：每條需求都有設計、實作、測試 → 防止遺漏

## 2. 追溯矩陣

### 📝 範本

| 需求編號 | 需求摘要 | 來源 | 優先序 | 設計（SDD 章節／API） | 實作（模組／類別） | 測試案例 | 測試結果 | 狀態 |
|---------|---------|------|-------|---------------------|------------------|---------|---------|------|
| {FR-xxx} | {摘要} | {BRD／CR 編號} | {Must／Should／Could} | {SDD x.y／`METHOD /path`} | {模組／類別} | {TC-xxx} | {Pass／Fail／未執行} | {✅／⏳／❌} |

### 📖 使用說明

- 非功能需求（NFR）通常由效能或安全測試驗證，「測試案例」欄填寫測試報告編號
- 需求異動（CR）時，同步更新受影響的列並記錄 CR 編號
- 狀態判定：設計、實作、測試三欄都有值且測試 Pass 才是 ✅

### 💡 範例

| 需求編號 | 需求摘要 | 來源 | 優先序 | 設計 | 實作 | 測試案例 | 測試結果 | 狀態 |
|---------|---------|------|-------|------|------|---------|---------|------|
| FR-LV-001 | 員工提交請假申請 | BRD 3.1 | Must | SDD 5.2／`POST /api/v1/leaves` | `leave-service`／`LeaveService` | TC-LV-001-01～04 | Pass | ✅ |
| FR-LV-002 | 特休額度不足時拒絕申請 | BRD 3.1 | Must | SDD 5.2／422 Problem Details | `LeaveQuotaPolicy` | TC-LV-002-01～02 | Pass | ✅ |
| FR-LV-005 | 主管代理人設定 | CR-2026-011 | Should | SDD 5.4 | `DelegateService` | TC-LV-005-01 | 未執行 | ⏳ |
| NFR-PERF-001 | 請假查詢 p95 < 500 ms（200 TPS） | SRD 4.1 | Must | SDD 8.1 快取 | `LeaveQueryService` | PT-RPT-2026-03（k6） | Fail（620 ms） | ❌ |

## 3. 自動追溯設定

### 📝 範本

```java
// 在自動化測試上標註需求編號（JUnit 5 以上）
@Tag("{需求編號}")
@DisplayName("{測試案例編號} {情境描述}")
@Test
void {測試方法名稱}() { /* ... */ }
```

```bash
# 前向追溯缺口：需求清單中有、但測試程式碼中找不到的需求編號
grep -ohE "^\| (FR|NFR)-[A-Z]+-[0-9]{3}" docs/requirements/rtm.md | tr -d '| ' | sort -u > req.txt
grep -rohE "@Tag\(\"(FR|NFR)-[A-Z]+-[0-9]{3}\"\)" src/test | grep -oE "(FR|NFR)-[A-Z]+-[0-9]{3}" | sort -u > tested.txt
comm -23 req.txt tested.txt    # 有輸出 → 有需求沒有自動化測試
comm -13 req.txt tested.txt    # 有輸出 → 有測試沒有對應需求（反向追溯缺口）
```

### 📖 使用說明

- 正規表示式需配合專案的需求編號格式調整
- 由效能或安全測試驗證的 NFR 不會有 `@Tag`，應在比對前從 `req.txt` 排除，或改以測試報告編號人工確認
- 建議在 CI 中執行，前向缺口數量做為 G2／G3 閘門的檢查項目

### 💡 範例

```java
@Tag("FR-LV-002")
@DisplayName("TC-LV-002-01 特休剩餘 2 天時申請 3 天，回傳 422")
@Test
void shouldRejectWhenAnnualLeaveQuotaInsufficient() { /* ... */ }
```

## 5. 審查與驗證

> 本節供審查者使用，也用來檢查 AI 依本範本產出的 RTM 是否正確。

### 自動檢查

| 檢查項目 | 方法 |
|---------|------|
| 前向／反向追溯 | 第 3 節的 `comm` 腳本，兩個輸出都應為空（或已列入第 4 節） |
| 需求編號唯一 | `grep -ohE "(FR\|NFR)-[A-Z]+-[0-9]{3}" rtm.md \| sort \| uniq -d` 應為空 |
| 測試結果與 CI 一致 | 「測試結果」欄與最近一次 CI 的測試報告比對 |

### 人工審查問題

1. 狀態 ✅ 的需求，測試是否真的驗證了需求（而非只是執行到程式）？
2. CR 核准後，受影響的列是否已更新？
3. NFR 是否都有對應的測試報告編號？
4. 反向缺口是否經 PO 判定？

### AI 常見錯誤

- 自行產生不存在的測試案例編號填滿表格，讓矩陣「看起來完整」。
- 把「已實作」當成「已驗證」。
- 漏列 NFR。

> 📌 **範本使用注意事項**
>
> 1. 優先以 CI 自動產生 RTM，人工只處理缺口
> 2. 搭配「FRD 範本」「測試案例範本」「需求異動申請範本」使用
> 3. G2 設計核准時檢查「設計」欄，G3 上線核准時檢查「測試結果」欄
