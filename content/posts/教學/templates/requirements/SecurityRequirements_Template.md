## 1. 文件資訊

### 📝 範本

| 項目 | 內容 |
|------|------|
| **文件編號** | SR-{專案代碼}-{序號} |
| **文件名稱** | {系統名稱} 安全需求清單 |
| **版本** | v{主版本}.{次版本} |
| **狀態** | 草稿 / 審核中 / 核定 |
| **建立日期** | {YYYY-MM-DD} |
| **撰寫者** | {姓名/角色} |
| **資安審核者** | {資安人員姓名} |
| **ASVS 版本／等級** | ASVS 5.0.0 / Level 1 / Level 2 / Level 3 |

### 📖 使用說明

- 依據 OWASP ASVS 5.0.0，安全需求分為三個驗證等級：
  - **Level 1**：所有應用程式的最低標準，大部分可用自動化工具驗證
  - **Level 2**：處理個資、金流等敏感資料的應用程式（大多數企業系統）
  - **Level 3**：最高安全等級（金流核心、身分驗證中心、關鍵基礎設施）
- 等級依專案風險分級選用（手冊 2.5、5.4）：風險 L1 高 → ASVS L2（關鍵元件 L3）；風險 L2 中 → ASVS L2；風險 L3 低 → ASVS L1
- 本清單在需求階段制定，貫穿整個 SDLC（設計需遵循、開發需實作、測試需驗證）
- ⚠️ **ASVS 5.0 的章節與需求編號已與 4.0.3 不同**（例如 4.0.3 的 V2 身分驗證在 5.0 為 V6）。引用時必須寫出版本，格式為 `v5.0.0-{章}.{節}.{條}`，例如 `v5.0.0-6.2.1`

### 💡 範例

| 項目 | 內容 |
|------|------|
| **文件編號** | SR-HRM-001 |
| **系統名稱** | 人力資源管理系統 |
| **ASVS 版本／等級** | ASVS 5.0.0 / Level 2（處理員工個資與薪資資料） |

## 3. 認證需求（Authentication）

### 📝 範本

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 | 實作狀態 |
|---------|---------|--------------|-------|----------|---------|
| SEC-AUTH-001 | {認證需求描述} | 6.{x}.{x} | L{N} | 必須/建議 | ☐ |
| SEC-AUTH-002 | {認證需求描述} | 6.{x}.{x} | L{N} | 必須/建議 | ☐ |

### 📖 使用說明

- 對應 OWASP ASVS 5.0 **V6（Authentication）**；密碼雜湊對應 **V11.4**；聯合身分（SSO）對應 **V6.8 與 V10（OAuth／OIDC）**
- Level 1：基本密碼安全；Level 2：多因子認證（MFA）或等效組合；Level 3：密碼學認證機制
- 認證需求需涵蓋：密碼策略、防暴力破解、MFA、密碼重設、SSO
- ⚠️ ASVS 5.0 的密碼政策與傳統作法不同：**不得**要求大小寫／數字／特殊字元等組成規則（6.2.5），**不得**強制定期更換密碼（6.2.10），改以長度、常見密碼與外洩密碼比對來提升強度

### 💡 範例

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 | 實作狀態 |
|---------|---------|--------------|-------|----------|---------|
| SEC-AUTH-001 | 密碼長度至少 12 字元（ASVS 下限 8、強烈建議 15）；允許至少 64 字元 | 6.2.1、6.2.9 | L1/L2 | 必須 | ☑ |
| SEC-AUTH-002 | 不設密碼組成規則，不強制定期更換；註冊與變更密碼時比對常見密碼清單與外洩密碼 | 6.2.5、6.2.10、6.2.4、6.2.12 | L1/L2 | 必須 | ☐ |
| SEC-AUTH-003 | 依文件定義的機制防禦帳密填充與暴力破解（每帳號連續失敗 5 次後延遲 15 分鐘，並對來源 IP 限流），不得造成惡意鎖定他人帳號 | 6.1.1、6.3.1 | L1 | 必須 | ☑ |
| SEC-AUTH-004 | 全體使用者啟用 MFA（或等效的多重單因子組合） | 6.3.3 | L2 | 必須 | ☑ |
| SEC-AUTH-005 | 密碼以 Argon2id 雜湊儲存（m=19 MiB、t=2、p=1 以上） | 11.4.2 | L2 | 必須 | ☑ |
| SEC-AUTH-006 | 整合企業 IdP 實現 SSO，並驗證斷言（JWT／SAML）的數位簽章 | 6.8.2 | L2 | 必須 | ☑ |
| SEC-AUTH-007 | 停用或移除預設帳號（admin、root、sa） | 6.3.2 | L1 | 必須 | ☑ |
| SEC-AUTH-008 | 密碼重設流程不得繞過已啟用的 MFA | 6.4.3 | L2 | 必須 | ☐ |

## 4. 授權與存取控制（Authorization）

### 📝 範本

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 | 實作狀態 |
|---------|---------|--------------|-------|----------|---------|
| SEC-AUTHZ-001 | {授權需求描述} | 8.{x}.{x} | L{N} | 必須/建議 | ☐ |

### 📖 使用說明

- 對應 OWASP ASVS 5.0 **V8（Authorization）**
- 遵循最小權限原則（Principle of Least Privilege）
- 需求涵蓋：功能層級（Function-level）、資料層級（Data-specific，防 IDOR／BOLA）、欄位層級（Field-level）授權
- 授權規則必須先寫成文件（8.1.1），測試才有判定依據

### 💡 範例

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 | 實作狀態 |
|---------|---------|--------------|-------|----------|---------|
| SEC-AUTHZ-001 | 授權文件定義各角色（Admin／Manager／Employee）可使用的功能與可存取的資料範圍 | 8.1.1 | L1 | 必須 | ☑ |
| SEC-AUTHZ-002 | 使用者僅能存取自己的薪資／假勤資料（資料層級授權，防 IDOR） | 8.2.2 | L1 | 必須 | ☑ |
| SEC-AUTHZ-003 | 每個 API 端點於伺服器端檢查功能權限，拒絕未授權請求回傳 403 | 8.2.1 | L1 | 必須 | ☑ |
| SEC-AUTHZ-004 | 主管只能讀取部屬薪資的「總額」欄位，不能讀取銀行帳號欄位 | 8.2.3 | L2 | 必須 | ☐ |
| SEC-AUTHZ-005 | 授權失敗事件需記錄於安全日誌 | 16.3.2 | L2 | 必須 | ☐ |

### 📖 使用說明

- 保護措施包含：傳輸加密、靜態加密（經認證的加密模式，例如 AES-GCM）、資料遮罩、存取控制、保留／銷毀策略

| 銀行帳號 | 高 | AES-256-GCM（靜態，金鑰存放於 KMS） | ****-****-1234 | 離職後 5 年 |

| Email | 低 | 無 | 無 | 離職後 2 年 |

| SEC-DATA-002 | 加密只使用經核准的演算法與模式（例如 AES-GCM） | 11.3.2 | L1 | 必須 |

## 6. 輸入驗證與輸出編碼

### 📝 範本

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 | 實作狀態 |
|---------|---------|--------------|-------|----------|---------|
| SEC-INPUT-001 | {輸入驗證需求} | 1.{x}.{x} / 2.{x}.{x} / 5.{x}.{x} | L{N} | 必須/建議 | ☐ |

### 📖 使用說明

- 對應 OWASP ASVS 5.0 **V1（Encoding and Sanitization）**、**V2（Validation and Business Logic）**、**V5（File Handling）**
- 防禦 OWASP Top 10:2025 的 A05 Injection（SQL Injection、XSS、Command Injection）
- 原則：永不信任使用者輸入，驗證必須在伺服器端（受信任的服務層）執行

### 💡 範例

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 |
|---------|---------|--------------|-------|----------|
| SEC-INPUT-001 | 所有輸入於伺服器端以允許清單（白名單）驗證 | 2.2.1、2.2.2 | L1 | 必須 |
| SEC-INPUT-002 | 資料庫查詢使用參數化查詢或 ORM，禁止字串拼接 | 1.2.4 | L1 | 必須 |
| SEC-INPUT-003 | HTML 輸出依上下文編碼（Context-Aware Encoding）防止 XSS | 1.2.1 | L1 | 必須 |
| SEC-INPUT-004 | 檔案上傳檢查副檔名與內容是否相符，並限制檔案大小 | 5.2.2、5.2.1 | L1 | 必須 |
| SEC-INPUT-005 | 文件定義每個上傳功能允許的檔案類型與大小上限（含解壓縮後大小） | 5.1.1 | L2 | 必須 |

## 7. Session 管理

### 📝 範本

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 | 實作狀態 |
|---------|---------|--------------|-------|----------|---------|
| SEC-SESS-001 | {Session 管理需求} | 7.{x}.{x} / 3.3.{x} | L{N} | 必須/建議 | ☐ |

### 📖 使用說明

- 對應 OWASP ASVS 5.0 **V7（Session Management）**；Cookie 屬性對應 **V3.3（Cookie Setup）**
- Session 管理攸關身分劫持風險
- 需求涵蓋：Token 產生方式、閒置與絕對逾時、登出後失效、Cookie 安全屬性

### 💡 範例

| 需求 ID | 需求描述 | ASVS 5.0 參照 | Level | 必須/建議 |
|---------|---------|--------------|-------|----------|
| SEC-SESS-001 | Session Token 以 CSPRNG 產生且至少 128 bits 熵 | 7.2.3 | L1 | 必須 |
| SEC-SESS-002 | Cookie 設定 `Secure` 並使用 `__Host-` 前綴；Session Cookie 設定 `HttpOnly`；`SameSite` 依用途設定 | 3.3.1、3.3.3、3.3.4、3.3.2 | L1/L2 | 必須 |
| SEC-SESS-003 | 閒置 30 分鐘、絕對 8 小時後需重新認證，並寫入設計文件 | 7.1.1、7.3.1、7.3.2 | L2 | 必須 |
| SEC-SESS-004 | 登入（含重新認證）後產生新的 Session Token，並使舊 Token 失效 | 7.2.4 | L1 | 必須 |
| SEC-SESS-005 | 使用者可檢視並終止其他裝置的 Session | 7.5.2 | L2 | 建議 |
| SEC-SESS-006 | 帳號停用（如員工離職）時終止其所有 Session | 7.4.2 | L1 | 必須 |

## 9. 通訊安全

### 📝 範本

## 13. 審查與驗證

### 自動檢查

| 檢查項目 | 方法 |
|---------|------|
| ASVS 編號存在且為 5.0 | 以 OWASP ASVS GitHub 的 `5.0/en` 章節檔比對每個 `{章}.{節}.{條}` 是否存在（`gh api repos/OWASP/ASVS/contents/5.0/en`） |
| 每條需求都有驗證方式 | 追溯矩陣「驗證方式」欄不得為空 |
| 輸入驗證、注入、日誌敏感資訊 | SAST（Semgrep `p/owasp-top-ten`）、Secrets 掃描（gitleaks） |
| TLS、HSTS、安全標頭 | `testssl.sh`、ZAP baseline 掃描 |
| 授權需求 | 每條授權需求至少一個「權限不足」與「存取他人資料」的整合測試 |

### 人工審查問題

1. ASVS 等級是否依專案風險等級選用？有沒有因為「做不完」而降級？
2. 每條需求的 ASVS 參照，內容真的與需求描述一致嗎？（抽查 5 條對照原文）
3. 密碼政策是否仍要求組成規則或定期更換（違反 ASVS 5.0 6.2.5、6.2.10）？
4. 威脅模型中的每個高風險威脅，都能在本清單找到對應的需求嗎？
5. 法規條款引用的是現行條文嗎？施行日期是否確認？

### AI 常見錯誤

- 沿用 ASVS 4.0.3 的章節與編號（例如把身分驗證寫成 V2.x），或捏造不存在的需求編號。
- 產生「90 天強制更換密碼」「必須包含大小寫與特殊字元」等已不符 ASVS 5.0 的密碼政策。
- 只列出需求，沒有寫驗證方式，導致測試階段無從驗證。
- 引用 OWASP Top 10:2021 的分類名稱（例如把注入寫成 A03）。
